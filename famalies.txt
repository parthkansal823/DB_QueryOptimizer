# The action space: every family of query optimization technique here

## What these are called

Three names, all correct, used in different places:

- **Action space** — the learned-optimizer term. Bao (Marcus et al., SIGMOD
  2021) frames query optimization as a contextual bandit: the query is the
  context, and each thing you can do to it is an *action*. That is the word
  used in `docs/WRITEUP.md` and throughout the code.
- **Hint families** / **hint classes** — the groupings below. One family is a
  set of hints that change the same *kind* of thing.
- **Query hints** or **plan hints** — an individual one. In PostgreSQL these
  are `pg_hint_plan` directives: a `/*+ ... */` comment before the statement.

pg_hint_plan has its own taxonomy, and it is worth knowing because it defines
what is *possible* rather than what this project happens to use:

| pg_hint_plan category | what it controls | used here |
|---|---|---|
| Scan method hints | how one table is read | yes |
| Join method hints | how two relations are joined | yes |
| Join order hints | the shape of the join tree | yes |
| Row number correction hints | the planner's cardinality estimate | yes |
| Parallel query hints | per-table parallel workers | partly (via GUC) |
| GUC hints (`Set`) | any planner or executor setting | yes |

A hint is a comment. PostgreSQL without the extension ignores it entirely,
which is why the "optimized" SQL this system hands you is safe to commit.

## The seven families

Counts are for a four-table query. They grow with table count.

| # | family | count | example |
|---|---|---|---|
| 1 | Join order (left-deep) | 8 | `/*+ Leading(c a d b) */` |
| 2 | Join order (bushy) | 2 | `/*+ Leading(((a b) (c d))) */` |
| 3 | Join method | 12 | `/*+ Leading(d b a c) HashJoin(d b) ... */` |
| 4 | Scan method | 9 | `/*+ SeqScan(a) */` |
| 5 | Operator toggles | 15 | `/*+ Set(enable_nestloop off) */` |
| 6 | Resource and cost model | 7 | `/*+ Set(work_mem 65536) */` |
| 7 | Cardinality correction | 1 | `/*+ Rows(a b *10) */` |
| | **total** | **54** | |

### 1. Join order — left-deep

```
/*+ Leading(orders users products) */
```

Names the order tables enter the join. PostgreSQL builds it **left-deep**:
`((orders ⋈ users) ⋈ products)`.

This is the family the project started with, and the one the whole premise
rests on: PostgreSQL picks a join order by minimising estimated cost, and when
the estimate is wrong the order is wrong with it.

Orders are drawn only from the query's own join graph, read off the baseline
plan's join conditions. A `Leading()` that introduces a table sharing no
predicate with those already placed forces a cartesian product, which
PostgreSQL prices at `disable_cost` (~1e10) and never picks — so blind
permutation sampling spends most of the budget on candidates that cannot be
used. On a 6-table chain join there are 720 orderings and only 32 connected
ones.

### 2. Join order — bushy

```
/*+ Leading(((orders users) (products suppliers))) */
```

The nested form specifies the join *tree*, not just an order. Two pairs are
built independently and then joined — a shape no left-deep ordering can
express.

It matters when both halves filter down hard. A left-deep tree has to carry the
first table's rows through every subsequent join; a bushy one builds two small
intermediates and joins those.

The project already knew this mattered before it could produce one:
`plan_tree.py` computes `tree_bushiness` as a model feature and its own comment
reads *"0.0 = perfectly left-deep (what Leading() produces)"*. The feature
encoder was measuring a property the generator could not vary. Neo and Bao both
search bushy plans.

Only balanced splits where both halves are internally connected *and* connected
to each other are produced — anything else is a cross product.

### 3. Join method

```
/*+ Leading(a b c) HashJoin(a b) HashJoin(a b c) */
```

Forces the algorithm used to join a given set of relations:

- **Hash join** — builds a hash table from one side. Fast for large unsorted
  inputs; spills to disk in batches if the build side does not fit `work_mem`.
- **Nested loop** — scans the inner side once per outer row. Excellent when the
  outer side is tiny and the inner is indexed; catastrophic when the outer side
  turns out large, which is exactly what a bad cardinality estimate causes.
- **Merge join** — needs both sides sorted. Cheap when they already are.

`Leading()` builds a left-deep tree, so the join nodes are the growing prefixes
`(a b)`, `(a b c)` — forcing one method across all of them approximates "use
this method throughout".

Off by default at serving time: it adds twelve planning round trips, and
`optimizer_overhead_ms` is what the production path lives or dies by.

### 4. Scan method — per table

```
/*+ SeqScan(orders) */    /*+ IndexScan(orders) */    /*+ BitmapScan(orders) */
```

How one table is read, leaving every other table alone.

This is the surgical version of family 5. `Set(enable_seqscan off)` bans
sequential scans for the **whole statement**, including on the small lookup
table where one is obviously right. `IndexScan(orders)` says "stop scanning
*this* table sequentially" and nothing else — which on a join between a large
filtered table and a small one is usually what was wanted.

- **Seq scan** — read every page. Right for most of a table, or a small one.
- **Index scan** — walk the index, fetch matching rows. Right for a few rows;
  random I/O, so `random_page_cost` decides how the planner prices it.
- **Bitmap scan** — collect matching pages from the index, then read them in
  physical order. The middle ground, and often the right one when the planner
  is choosing badly between the other two.

### 5. Operator toggles — statement-wide

```
/*+ Set(enable_nestloop off) */
/*+ Set(enable_nestloop off) Set(enable_mergejoin off) */   → forces hash joins
```

Bao's own action space, and the reason it exists: join *order* alone is a weak
space. On a two-table query there are two orderings and PostgreSQL already
picks the better one, so every "candidate" comes back as the same plan and the
optimizer cannot possibly improve anything. Toggling a whole class of operator
off makes the planner re-plan under a restriction, which produces a genuinely
different plan with a genuinely different cost.

PostgreSQL never truly disables an operator — it prices it at `disable_cost`
and lets the arithmetic bury it — so no combination here can fail to produce a
plan.

Twelve join/scan combinations, plus:

- `enable_material` — materialising an inner side to avoid re-scanning it.
- `enable_memoize` (PG14+) — caches the inner side of a nested loop across
  repeated parameter values. A large win when the outer side repeats, pure
  overhead when it does not, and the planner decides from the estimate.
- `enable_hashagg` — hash aggregation can spill; a sorted group-by sometimes
  wins.
- `enable_incremental_sort` — exploits an already-partially-sorted input, and
  loses to a plain sort when the planner is wrong about how sorted it is.

### 6. Resource and cost model

```
/*+ Set(work_mem 65536) */    /*+ Set(max_parallel_workers_per_gather 4) */
/*+ Set(jit off) */           /*+ Set(geqo_threshold 20) */
```

Every family above changes the *shape* of the plan. None of them changes what
the executor is given to work with, and on a starved server that is the larger
lever.

- **`work_mem`** (in kB) — a hash join whose table does not fit spills to disk
  in batches; a sort that does not fit becomes an external merge. Both are
  large, cliff-edged effects the planner prices only through its estimate of
  the input size. Measured here: cost 23264 → 17792 on a three-table join.
- **`max_parallel_workers_per_gather`** — forcing workers on turns a sequential
  scan of a large table parallel; forcing them off removes a Gather whose
  startup cost is not repaid on a small result.
- **`random_page_cost`** — 4.0 encodes a seek-heavy spinning disk. On SSD it
  prices index scans far above what they cost, biasing everything toward
  sequential scans.
- **`join_collapse_limit 1`** — pins the join order written in the query and
  stops subquery pull-up. Genuinely different from any `Leading()` hint.
- **`jit off`** — JIT is a fixed cost paid before the first row, priced by the
  planner's cost estimate. On a query the planner *thinks* is expensive and is
  not, compiling can take longer than executing.
- **`geqo_threshold 20`** — above 12 joined relations PostgreSQL abandons
  exhaustive search for a genetic algorithm: fast, approximate, and
  **non-deterministic**, so the same query can get different plans on different
  runs. This is the setting that matters most on JOB's 8-to-17 table queries.

### 7. Cardinality correction

```
/*+ Rows(orders users *10) */
```

The only family that does not force anything. It hands the planner a corrected
row estimate and lets it decide for itself, so the plan that comes back can be
one no `Leading()` or `Set()` can express.

Produced by `optimizer/cardinality.py`, which learns PostgreSQL's own q-error
from `Plan Rows` against `Actual Rows` — the root cause Leis et al. identified.

Written up as a **null result** in `docs/WRITEUP.md` §2.8.1: it is verified to
bind (a join estimated at 4 rows reports 400 under `Rows(o u *100)`) and beats
native by up to 83% on the correlation traps, but it raises the oracle ceiling
by **0.0%**, because every win it found was already reachable through the
existing hints. Kept for the JOB-scale case it was built for.

`app/dbadvisor/extended_stats.py` attacks the same problem permanently, with
`CREATE STATISTICS`, rather than one query at a time.

## How a query's action space is assembled

`optimizer/planner.py::candidate_hints` builds the list, and then:

1. **The regression guard removes families that have lost on this query.**
   Blocking a whole query is blunt — usually one *kind* of action is bad on it,
   not all of them.
2. **The budget truncates by estimated cost.** A query PostgreSQL prices at a
   few hundred cost units cannot repay a twenty-candidate search, and the
   families are ordered so the resource settings — the ones that cannot help a
   small query — are dropped first.
3. **Duplicate plans are dropped.** Most hints on a simple query reproduce the
   native plan; counting those as candidates makes the action space look bigger
   than it is and guarantees a 0% improvement.

The same function serves `/query/optimize` and `/query/analyze`, so the two
cannot explore different spaces — that kind of train/serve skew is what
`docs/WRITEUP.md` §2.9 documents.

## What is deliberately not in the action space

- **Query rewriting.** Changing the SQL rather than the plan — pushing down a
  predicate, turning a subquery into a join. Higher ceiling, and it has to
  preserve semantics exactly, which a hint gets for free.
- **`IndexOnlyScan` / `NoIndexScan` / per-table `Parallel()`.** pg_hint_plan
  supports them; they are not generated yet.
- **Materialized views, partitioning, sharding.** Schema redesigns, not plan
  choices.
- **Multi-query optimization.** Sharing work across a workload rather than
  optimising each query alone.

## Turning families on and off

| setting | default | family |
|---|---|---|
| `INCLUDE_JOIN_METHODS` | off | 3 |
| `INCLUDE_TUNING` | on | 6 |
| `ENABLE_ROWS_CORRECTION` | on | 7 |
| `ADAPTIVE_CANDIDATE_BUDGET` | on | truncation |

All are editable from the dashboard's settings panel and persist in
`models/settings.json`.

**Widening the action space is not free**, and the project has been bitten by
it: doing so without retraining sent 17 of 25 queries into the safety veto,
because the model was scoring plan types it had never seen. If you turn a
family on, re-run `app.collect_data` — and settle whether it actually helped
with `app.experiment`, not by reading three numbers off one run.

## Where these come from — sources

### The hint syntax itself (family 1–7, all of it)

- **pg_hint_plan, official documentation** — the complete hint list, the six
  categories in the table at the top of this file, and the exact syntax for
  `Leading`, the nested bushy form, `HashJoin`/`NestLoop`/`MergeJoin`,
  `SeqScan`/`IndexScan`/`BitmapScan`/`IndexOnlyScan`, `Rows`, `Parallel`, `Set`.
  https://pg-hint-plan.readthedocs.io/en/latest/hint_list.html
- **pg_hint_plan source** — when the docs and the behaviour disagree, this is
  what is actually running. https://github.com/ossc-db/pg_hint_plan
- **Why hints get silently ignored** (the §2.0 bug this project hit):
  https://pg-hint-plan.readthedocs.io/en/latest/hint_details.html

### The settings behind families 5 and 6

- **PostgreSQL: Planner Method Configuration** — every `enable_*` toggle,
  including `enable_memoize`, `enable_hashagg`, `enable_incremental_sort`.
  https://www.postgresql.org/docs/current/runtime-config-query.html#RUNTIME-CONFIG-QUERY-ENABLE
- **PostgreSQL: Planner Cost Constants** — `random_page_cost`, `seq_page_cost`,
  `cpu_tuple_cost`.
  https://www.postgresql.org/docs/current/runtime-config-query.html#RUNTIME-CONFIG-QUERY-CONSTANTS
- **PostgreSQL: Genetic Query Optimizer** — what `geqo_threshold` switches on,
  and why it is non-deterministic.
  https://www.postgresql.org/docs/current/geqo.html
- **PostgreSQL: `work_mem`** — the spill-to-disk cliff.
  https://www.postgresql.org/docs/current/runtime-config-resource.html#GUC-WORK-MEM
- **PostgreSQL: JIT** — `jit`, `jit_above_cost`, and why it can cost more than
  it saves. https://www.postgresql.org/docs/current/jit-decision.html
- **PostgreSQL: `join_collapse_limit` / `from_collapse_limit`** — the explicit
  join-order pin. https://www.postgresql.org/docs/current/explicit-joins.html

### The idea of an "action space"

- **Bao: Making Learned Query Optimization Practical** — Marcus, Negi,
  Mao, Tatbul, Kraska, Alizadeh. SIGMOD 2021. Where the term comes from, and
  where family 5 (statement-wide operator toggles as the action space) is from.
  https://arxiv.org/abs/2004.03814
- **Neo: A Learned Query Optimizer** — Marcus et al., VLDB 2019. Learns the
  plan tree end to end, which is where bushy search (family 2) and plan-tree
  encoding come from. https://arxiv.org/abs/1904.03711
- **Lero: A Learning-to-Rank Query Optimizer** — Zhu et al., VLDB 2023. The
  pairwise ranking objective used in `learned_pairwise_rank`.
  https://arxiv.org/abs/2302.06873

### Why cardinality correction (family 7) exists

- **How Good Are Query Optimizers, Really?** — Leis, Gubichev, Mirchev,
  Boncz, Kemper, Neumann. VLDB 2015. The paper that established estimation
  error, not the search or cost model, as the dominant source of bad plans.
  https://www.vldb.org/pvldb/vol9/p204-leis.pdf
- **Join Order Benchmark (JOB)** — the 113 queries from that paper.
  https://github.com/gregrahn/join-order-benchmark
- **PostgreSQL: `CREATE STATISTICS`** — the permanent fix `dbadvisor` proposes
  instead of a per-query `Rows()` hint.
  https://www.postgresql.org/docs/current/sql-createstatistics.html
- **PostgreSQL: Row Estimation Examples** — how the estimates being corrected
  are computed in the first place.
  https://www.postgresql.org/docs/current/row-estimation-examples.html
